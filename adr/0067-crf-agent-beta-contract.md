# ADR 0067: Review-gated CRF agent beta over local study drafts

## Status

Accepted for implementation planning. AI activation remains subject to #2674 and release hold #2691.

## Context

ADR 0014 isolates Clerk to admin work so public pages and local CRF editing do not depend on authentication. ADR 0021 defines the universal `StudyProtocol` and pure engine; ADR 0022 defines manual Studio surfaces. The proposed invite-only assistant adds an inference boundary and a new way to author study **design metadata**. It must not turn model text into a trusted study mutation, and it must not confuse design lint with regulatory conformance. The design-only ADR 0035 left live-provider decisions open; this ADR resolves their beta architecture while retaining its review boundary. Earlier exploration in #665 did not include a live provider; #1148 asked for a concrete reason to add public sign-in. Protected, reviewed AI proposals are that reason.

## Decision

The October 28 target is a conditional **synthetic-data beta**, not authority to release. `/crf` and `/m/crf` keep anonymous study creation, editing, local draft recovery, Visit Matrix, validation, simulation, import, and manual export. Only the AI panel and inference requests require a signed-in, separately entitled author. The model produces proposals and explanations; the existing CRF engine decides whether a proposal is structurally valid; a human decides whether to apply it. Apply is a single undoable Studio edit. No account-owned study store, participant records, e-signatures, automatic exports, or automatic publication are in this slice.

### Identity and entry points

Use Clerk already present in the repo, but give the agent an independent, default-deny `CRF_AGENT_USER_IDS` server-side entitlement. Never infer it from `ADMIN_USER_IDS` or `ADMIN_EMAILS`, client claims, or a visible button. `/crf/agent/login` is the sign-in and return route (`app/crf/agent/login/[[...rest]]/page.tsx`); an author returns to the same `/crf` or `/m/crf` workspace after auth. The local draft remains in browser storage throughout sign-in, sign-out and denial. Both workspaces show a small optional AI entry point; the manual editing controls remain usable in all states.

| State                                                   | Desktop and mobile behavior                                                         | Server AI response       |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------ |
| Anonymous                                               | Manual Studio works; AI entry offers sign-in                                        | 401                      |
| Signed in, unentitled or revoked                        | Manual Studio works; access-denied screen offers sign-out/return                    | 403                      |
| Entitled, consent not given this session                | Manual Studio works; AI entry shows disclosure and consent                          | No context sent          |
| Entitled and consented                                  | Reviewable suggestions can be requested; Apply still requires explicit human action | Bounded inference only   |
| Missing Clerk keys, provider outage or exhausted budget | Manual Studio works; AI explains unavailability                                     | Fail closed, no mutation |

Implement #2663 with a route-scoped Clerk provider and server check at each AI endpoint. Extend `proxy.ts` only for AI auth paths; retain the security-header and API connection-hash behavior. `/crf` and `/m/crf` must not be Clerk-gated or call Clerk merely to render. The installed Next.js authentication guide requires authorization inside Route Handlers or Server Actions as well as UI checks; proxy checks alone are insufficient. Coordinate invite-only provider sign-up policy with #627 before enrollment.

### Agent module and review contract

`lib/crf` exposes one public proposal facade. Input is `{ contractVersion, baseStudyRevision, boundedContext, candidateOperations }`; output is a strict discriminated union of `{ status: "ready", proposal, semanticDiff, assumptions, evidence, warnings, affectedReferences }` or typed rejection (`invalid`, `stale`, `unsupported`, `unavailable`, `quota`). A candidate operation is a versioned Zod allowlist entry, never code, a URL to fetch, a raw `StudyProtocol` replacement, or a client-authorized tool call. `boundedContext` includes only the selected synthetic design metadata needed for the requested action. It is not a full browser draft dump by default.

The proposal stores a digest/revision of the study it was computed from. The engine checks that revision again at Apply, validates the operation allowlist and complete resulting `StudyProtocol`, then runs existing reference, codelist, rule, and conformance checks. Blocking errors prevent Apply; warnings and assumptions stay visible. The preview names affected fields, forms, visits, assignments, rules, tests and mappings, including cross-visit references. An overwrite, unassignment, deletion, or material window/order change requires an additional explicit impact acknowledgment. Reject, revise, malformed output and auth loss leave the study untouched. A stale proposal is rejected with a regeneration path; it never overwrites newer manual edits. An accepted result enters `useStudyHistory.commit` through `useStudyEditor` as **one** edit so Undo restores the exact prior draft. Existing local draft persistence remains the storage contract. #2666 builds this seam before any authoring action; #2667 then #2668 add operations through it.

Each suggested change has provenance `{ proposalId, operationId, sourceKind, sourceId, sourceLocation?, excerpt?, standardName?, standardVersion?, catalogVersion?, generatedAt, modelId?, assumptions, reviewerDisposition? }`. Source locations refer to synthetic supplied material or an identified local catalog item. No source means “model hypothesis / needs review,” never an invented citation. Provenance is attached to the proposal/review record, not silently written into regulated clinical records. Local history and baselines are useful for design review but are not Part 11 audit or e-signature certification.

### Findings, facts and hypotheses

- **Deterministic finding:** a reproducible result from a named schema, linter, evaluator or simulator version against a specified study revision. It can pass, warn or fail only for that rule's implemented scope.
- **Source-backed fact:** a statement tied to a reviewable protocol excerpt or named, versioned standard/catalog entry. A reviewer checks whether the cited source supports this study-specific use.
- **Model hypothesis:** an inference or suggested requirement without deterministic proof or a source sufficient to establish it. It is visibly marked “needs review.”

No model explanation, inferred endpoint, generated mapping or missing-rule guess is displayed as a passed conformance result. CDISC CORE, if integrated later, remains an independently versioned deterministic rules engine. The separate Study Data Pipeline in ADR 0065 remains LLM-free; #2679 may add a read-only explanation overlay after beta.

### Standards and catalog boundary

Pin the beta's implemented design lint to **CDASHIG 2.2 and SDTMIG 3.4**. CDISC has published CDASHIG 2.3, which is a separate compatibility and regression decision for #2677; it must not silently change rule semantics. CDISC Controlled Terminology has a **2026-09-25 P62** release, but the repository's `STANDARD_CODELISTS` is a hand-curated set of 18 codelists without a declared package version. `CDASH_STANDARD_VARIABLES` covers 12 domain keys (`DM`, `VS`, `AE`, `CM`, `LB`, `DI`, `DU`, `DE`, `DA`, `EX`, `MH`, `DS`) and is not the full CDASH catalog. Do not label local snippets as P62 or claim full CDISC conformance. #2677 must verify terms, package version, redistribution/licensing and any instrument rights before promoting source-backed standard suggestions. Validated questionnaires and rating scales must not be paraphrased or restructured by the agent.

### Inference, privacy and cost decision

Use the existing Vercel stack: server-side AI SDK through Vercel AI Gateway with an initial **`openai/gpt-5-mini`** model allowlist for synthetic text-only design suggestions. The current Gateway catalog lists that model at $0.25 input / $2 output per million tokens; #2665 must recheck availability, routing and price at implementation time. No provider key reaches the browser. Do not enable a fallback model/provider silently. If the chosen route cannot meet the policy, fail closed while manual authoring continues.

The author opts in before the first request of **each session** and sees exactly which selected metadata will leave the browser. Beta requests accept synthetic study specifications only: no PHI, participant rows, live EDC exports, arbitrary URL retrieval, or raw protocol attachments. #2664 enforces field-level context selection, size limits, server schema checks, cancel/reset and no-content logging. The gateway says it does not retain prompt/output content after a request; upstream provider retention is separate. Gateway provider-level zero-data-retention controls are Pro/Enterprise features, so this free-tier beta must **not** promise provider ZDR. Operators must confirm the selected provider's current retention and training terms and put them in the consent copy before enrollment. Until then, AI remains disabled. No raw prompt/output in URLs, analytics, Sentry, console or operational telemetry; retain only opaque request ID, token count, latency, error category and estimated cost. No server-side study or prompt history is retained by this application.

Set the beta kill switch default off. For the first enrollment, cap each request at 8,000 input and 2,000 output tokens, 30 seconds and one model step; cap each entitled author at 20 requests per day, all authors at 100 requests per day, and app-side estimated spend at **$4 per rolling 30 days**. Reserve the worst-case estimated request cost before calling the provider and reconcile actual usage afterward; reject when the reservation would cross a cap. #2665 must enforce those caps and a maximum serialized proposal size of 256 KiB server-side. The Gateway documents a $5 monthly free credit and budget controls, but budget checks are a **soft** per-request cap and BYOK spend is not counted; the app-side reservation/limit is required. Do not buy credits or switch to BYOK automatically. If free credits or verified terms are unavailable, inference remains disabled. An operator must enroll/revoke named beta users, verify the Gateway project budget and privacy settings, and approve the selected provider's retention terms and consent copy before #2674 can enable the beta. Operators may lower the caps; raising them requires a new cost decision.

## Release slice and consequences

1. #2663 adds scoped identity and independent entitlement. #2664 adds consent and bounded context. #2665 adds a disabled-by-default, cost-bounded inference route. #2666 adds the typed, stale-safe proposal facade.
2. #2667, #2668 and #2669 add authoring operations. #2676, #2677 and #2678 add clinical traceability, versioned terminology safeguards and amendment impact. #2670 and #2671 add read-only explanations. #2672 integrates accessible review and undo on desktop/mobile.
3. #2673 evaluates adversarial output, anonymous/manual access, invalid references, synthetic journeys and privacy/cost boundaries. #2674 records operator settings, named reviewers and the beta go/no-go. Human-first UX gate #2687 also applies.
4. Keep AI off if any gate fails. #2691 holds production until its **entire** scope is complete; no date or passing CRF subset overrides it. Follow ADR 0051 for a later operator-initiated production release.

This keeps the local Studio responsive and usable during auth/provider failure. The cost is a separate entitlement, a stricter proposal protocol and explicit review work, which are necessary because model output is untrusted and clinical design decisions require accountable human judgment.
